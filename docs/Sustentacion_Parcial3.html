1. Explicación del Parcial y Objetivo de Ospedale

El proyecto Ospedale representa un sistema académico de gestión hospitalaria cuyo propósito funcional es administrar la autenticación de usuarios y coordinar las operaciones médicas clave entre tres roles principales: Administradores, Pacientes y Doctores. Estas operaciones incluyen el registro y actualización de perfiles de usuario, la solicitud, aceptación y finalización de citas médicas, la reprogramación de consultas, la prescripción de tratamientos farmacológicos, y la solicitud y aprobación de hospitalizaciones clínicas.

Desde una perspectiva de ingeniería de software, el objetivo primordial del parcial consiste en realizar una refactorización estructural completa y profunda sobre una base de código acoplada. El desafío radica en separar de manera tajante la presentación visual de la lógica de negocio y las persistencias, migrando el sistema hacia un patrón de arquitectura Model-View-Controller (MVC) y aplicando estrictamente los principios de diseño SOLID. Con esta transformación se busca lograr un sistema de alta cohesión, bajo acoplamiento, extensibilidad nativa ante futuros requerimientos, y una sincronización reactiva automatizada entre la base de datos simulada y la interfaz de usuario Swing.

3. Aplicación y Flujo del Patrón MVC (Model-View-Controller)

La arquitectura del sistema garantiza que la Vista y el Modelo no se comuniquen directamente, cumpliendo con el estándar estricto de MVC. Las vistas solo interactúan con interfaces controladoras, y estas delegan la lógica de negocio a servicios especializados que recuperan y persisten datos a través de repositorios. El retorno de información se orquesta mediante el objeto envolvente Response, el cual transporta mapas serializados en lugar de objetos modelo crudos.

4. Aplicación de la Arquitectura SOLID

El diseño del software se fundamenta en los cinco principios SOLID para asegurar estabilidad y flexibilidad ante cambios:

  • S - Single Responsibility Principle (Principio de Responsabilidad Única): Cada clase tiene una única razón de cambio. Las vistas (Login, Patient_View) son exclusivamente responsables de capturar eventos de entrada y pintar componentes; los validadores (PatientValidator, DoctorValidator) de verificar formatos; los servicios (PatientServiceImpl) de aplicar las reglas de negocio y consistencia; y los repositorios (PatientRepositoryImpl) del acceso físico al origen de datos.
  • O - Open/Closed Principle (Principio de Abierto/Cerrado): Las entidades y servicios son extensibles sin modificar clases base existentes. Por ejemplo, el subsistema de Hospitalización (HospitalizationService, HospitalizationRepository) se integró extendiendo el modelo de citas y agregando repositorios especializados, sin alterar la lógica core del servicio de pacientes o de citas existente.
  • L - Liskov Substitution Principle (Principio de Sustitución de Liskov): La clase abstracta User define la identidad fundamental. Sus subclases concretas Patient, Doctor y Administrator pueden ser tratadas indistintamente como instancias de User en colecciones genéricas o procesos de autenticación (Storage.users) sin corromper el comportamiento en ejecución.
  • I - Interface Segregation Principle (Principio de Segregación de Interfaces): Se crearon contratos de interfaz altamente especializados (PatientRepository, AppointmentRepository) en lugar de una interfaz de datos única y monolítica. Así, el servicio PatientServiceImpl no tiene acoplamiento ni conocimiento de métodos de citas, prescripciones o camas de hospitalización.
  • D - Dependency Inversion Principle (Principio de Inversión de Dependencias): Los módulos de alto nivel (Servicios) no dependen de módulos de bajo nivel (Detalle del almacenamiento). En cambio, ambos dependen de abstracciones. PatientServiceImpl recibe en su constructor la interfaz PatientRepository, lo que permite cambiar el motor de almacenamiento de Storage en memoria a una Base de Datos SQL sin modificar una sola línea de lógica del negocio.
ControllerRegistry.java - Inversión de Dependencias (DIP) y Orquestación de Capas
public class ControllerRegistry { private static ControllerRegistry instance; private final IPatientController patientController; private ControllerRegistry() { // 1. Instanciar detalles de almacenamiento (Bajo Nivel) PatientRepository patientRepository = new PatientRepositoryImpl(); // 2. Inyectar en los servicios abstractos (Alto Nivel) IPatientService patientService = new PatientServiceImpl(patientRepository); // 3. Inyectar servicio en el controlador this.patientController = new PatientController(patientService); } // ... }

6. Explicación de los Bonos de Calificación

Bono 1: SOLID Aplicado en los Controladores del Proyecto

El primer bono de calificación del parcial (0.5 pts) requería estructurar los controladores bajo principios de diseño SOLID. En el diseño legacy, los controladores contenían responsabilidades de orquestación, lógica de negocio e incluso de formato de strings. En la versión refactorizada, se aplicó la inversión y segregación de la siguiente manera:

  1. Interfaces Segregadas (ISP): Se definieron las interfaces IAuthController, IPatientController, IDoctorController y IMedicalServiceController. Los controladores concretos se limitan a implementar estos contratos y no se acoplan a otras operaciones de la aplicación.
  2. Fachadas Cohesivas y Delgadas (SRP): El controlador ya no contiene lógica algorítmica ni condicionales del negocio. Su única responsabilidad es recibir los datos de la interfaz (en formato String plano), despacharlos al servicio adecuado y retornar la estructura serializada Response.
  3. Desacoplamiento total mediante DIP: Ningún controlador instancia de forma directa su respectivo servicio. En su lugar, el servicio correspondiente (por ejemplo, IPatientService) es inyectado como una interfaz a través de su constructor, siendo el componente centralizador ControllerRegistry el encargado de proveer la instancia concreta durante el inicio de la aplicación.

Bono 2: Patrón de Diseño Observer para Actualización de Tablas

El segundo bono del parcial (0.5 pts) exigía implementar el patrón observador para actualizar automáticamente las tablas de la interfaz gráfica Swing ante cambios en el modelo, eliminando la necesidad de implementar botones manuales de refresco. La solución se estructuró a través del desacoplamiento de suscripción reactiva:

  • El Sujeto Observable (Subject): La clase Storage (que simula el almacenamiento centralizado) mantiene una colección segura para entornos concurrentes de observadores (CopyOnWriteArrayList<StorageObserver>) y expone las rutinas de suscripción:
    public void addObserver(StorageObserver observer) { if (observer != null && !observers.contains(observer)) { observers.add(observer); } } public void publishEvent(StorageEventType eventType) { for (StorageObserver observer : observers) { observer.onStorageChanged(eventType); } }
  • El Canal de Eventos y el Contrato: Se crearon la interfaz funcional StorageObserver (con el método callback onStorageChanged(StorageEventType)) y el enum de canales de actualización StorageEventType (que cuenta con las etiquetas USERS_CHANGED, APPOINTMENTS_CHANGED y HOSPITALIZATIONS_CHANGED).
  • Los Observadores Concretos (Vistas): Al arrancar, las vistasSwing (Patient_View, Doctor_View, Admin_View) se suscriben como observadores implementando una expresión Lambda reactiva. Para asegurar que las modificaciones visuales de las tablas se realicen en el hilo adecuado del sistema Swing, el callback ejecuta sus rutinas visuales dentro de SwingUtilities.invokeLater():
    private void registerObserver() { storageObserver = eventType -> SwingUtilities.invokeLater(() -> { if (eventType == StorageEventType.APPOINTMENTS_CHANGED) { loadAppointmentsTable(); // Actualiza la JTable de forma automática y transparente } }); Storage.getInstance().addObserver(storageObserver); }
  • Evitar fugas de memoria (Memory Leaks): Las vistas implementan un WindowAdapter para remover su suscripción al almacenamiento (removeObserver) cuando se cierra la ventana (dispose()), liberando recursos de manera limpia.

7. Guía y Consejos para una Sustentación Excelente (5.0)

Para asegurar una nota perfecta (5.0) en la sustentación del examen parcial ante el profesor del Departamento de Ingeniería de Sistemas, se recomienda enfocar la defensa oral y técnica en los siguientes tres pilares estratégicos:

Pregunta o Foco Común Estrategia y Argumentación de Defensa Técnica
¿Por qué el controlador no valida los formatos de email o ID? Explique que por el principio de Responsabilidad Única (SRP), el controlador es solo un traductor de la capa de presentación hacia el dominio. Validar formatos es una tarea de infraestructura/utilidades que pertenece al paquete validator, mientras que validar la lógica del negocio (ej. unicidad o disponibilidad) es responsabilidad exclusiva de la capa de service. Esto permite reutilizar el validador en múltiples flujos (registro, actualización) sin duplicar código.
¿Cómo se inyectan las dependencias en este proyecto? Señale la clase ControllerRegistry.java. Explique que en ausencia de un framework como Spring, se implementó un Contenedor manual de Inyección de Dependencias (DI) bajo el patrón Singleton. Este registro instancia los componentes de abajo hacia arriba (Repositorio concreto → Servicio con dependencias de interfaz → Controlador con dependencias de interfaz), cumpliendo con el principio de Inversión de Dependencias (DIP).
¿Por qué se retorna serialización en lugar del objeto modelo crudo? Responda que si la vista Swing recibiera objetos como Patient o Appointment, esta tendría acceso directo a mutar sus atributos mediante setters o acceder a relaciones internas, rompiendo la encapsulación y generando un acoplamiento fuerte. Al mapear las entidades a estructuras de datos planas (HashMap<String, Object>), la vista solo puede leer los atributos expuestos para renderizado, garantizando que el estado del negocio sea inmutable desde la UI.
¿Cómo previene el Observer problemas de concurrencia y congelamiento de UI? Enfatice que el callback del observador en las vistas Swing utiliza SwingUtilities.invokeLater(). Swing no es seguro para hilos (thread-safe), por lo que cualquier actualización asíncrona de tablas en la JTable gatillada desde el motor Storage debe encolarse en el Event Dispatch Thread (EDT). Esto previene hilos en conflicto y asegura una interfaz fluida.
